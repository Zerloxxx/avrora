## 5. Глубина рассуждений — сколько думать перед действием

Не думать одинаково над всем. Уровень усилий выбирается по цене ошибки и обратимости:

| Класс задачи | Как действовать | Планирование |
|---|---|---|
| **Тривиальное** (опечатка, переименование, правка строки, известный паттерн) | Сразу делаю, без прелюдий | Не нужно |
| **Локальная фича / понятный баг** | Коротко проверяю окружение (как сделано рядом) → делаю | План в голове; TODO-список если >3 шагов |
| **Фича на несколько файлов / новый модуль / затрагивает API-контракт** | Сначала план, потом код. Читаю смежный код и `CONTEXT.md` перед стартом | Явный план + TODO-лист (TaskCreate) |
| **Архитектурное решение / необратимое / много вариантов** | Проектирую дважды: минимум 2 подхода, выбираю с обоснованием. Спорное — фиксирую в ADR | План-режим, при неясности — вопрос пользователю |
| **Диагностика неочевидного бага** | Гипотезы → проверка каждой → фикс. Не гадать, не «менять наугад» | Цикл гипотеза→эксперимент→вывод |

**Правила поверх таблицы:**
- **Есть достаточно данных — действую.** Не пересказываю варианты, которые не буду делать, не переспрашиваю то, что видно в коде.
- **Спрашиваю только то, что реально решает пользователь** — развилки в требованиях, а не выбор с очевидным дефолтом. Выбор с дефолтом — беру дефолт, называю его, иду дальше.
- **Необратимое и внешнее — подтверждаю до, а не после.** Удаление, перезапись, публикация, отправка наружу, деструктивный git. Разрешение в одном месте не переносится на следующее.
- **Перед удалением/перезаписью смотрю на цель.** Если содержимое противоречит тому, как его описали, — сообщаю, а не выполняю.
- **Не изобретаю преждевременных абстракций.** Обобщаю на третьем повторении, не на первом.

## 6. Как агент ведёт работу

- **Читаю перед тем как писать.** Перед работой в области — соответствующий `CONTEXT.md` (глоссарий) и релевантные ADR. Файлов нет — молча продолжаю, не флагаю их отсутствие.
- **Многошаговое — через TODO-лист** (TaskCreate/TaskUpdate): в работе один пункт за раз, отмечаю выполненным сразу по факту. Это делает прогресс видимым и не даёт потерять шаги.
- **Пишу код в стиле окружения:** имена, идиомы, плотность комментариев — как в соседних файлах.
- **Проверяю результат, а не только «скомпилировалось».** Нетривиальную правку прогоняю по реальному сценарию (запуск/тест затронутого потока), прежде чем сказать «готово».
- **Отчитываюсь честно.** Тесты упали — говорю прямо с выводом. Шаг пропустил — говорю. Сделано и проверено — говорю без хеджирования.
- **Использую специализированные сценарии (скиллы) вместо импровизации**, когда задача под них подходит (см. раздел 10).

## 7. Как и куда записывать знания (обязательно)

Цель — чтобы знание из разговора не терялось и следующий агент не переоткрывал его заново.

**Правило маршрутизации — куда сохранять новое знание:**
| Что появилось | Куда пишем |
|---|---|
| Новый доменный термин | `CONTEXT.md` той области (формат — раздел 7.1) |
| Паттерн / баг+фикс / gotcha / решение по коду | `{область}/CLAUDE.md` (backend → `backend/CLAUDE.md`, web → `web/CLAUDE.md`, …) |
| Архитектурное решение с альтернативами и последствиями | новый файл в `docs/adr/` (или `{область}/docs/adr/`) |
| Общее для всего проекта (стек, стиль, дедлайны, порядок работы) | этот файл (`CLAUDE.md`) |

**Когда писать:** сразу после каждой новой фичи, изменения поведения, найденного бага/решения или важного паттерна — **не откладывать «на потом» и не ждать отдельной просьбы.**

**Как писать, чтобы дока не расходилась с кодом:**
- Правка меняет уже описанное поведение → **править/удалять старый текст**, а не дописывать рядом.
- В корневом `CLAUDE.md` детали не дублировать — достаточно упомянуть, что фича реализована, детали живут в `{область}/CLAUDE.md`.
- Формулировать конкретно: не «поправил сборку», а «X падает потому что Y; фикс — Z» (чтобы запись экономила время, а не пересказывала diff).
- Пишу только то, что **не** выводится из кода/git. Структуру файлов и историю коммитов дублировать не нужно.

### 7.1. Формат CONTEXT.md (глоссарий домена)

```md
# {Название области}

{Одно-два предложения: что это за область и зачем.}

## Language

**{Термин}**:
{Что это ЕСТЬ, одно-два предложения. Не что делает — чем является.}
_Avoid_: {синонимы, которые НЕ используем}
```
Правила: быть категоричным (один термин на концепт, остальные в `_Avoid_`); только термины, специфичные для домена (общие программистские понятия не включать); определения короткие.

### 7.2. Формат ADR (архитектурное решение)

```md
# ADR-{NNNN}: {Заголовок решения}

Status: {proposed | accepted | superseded by ADR-XXXX}
Date: {YYYY-MM-DD}

## Context
{Проблема и силы, которые на неё давят.}

## Decision
{Что решили.}

## Consequences
{Что теперь так, чем платим, что стало проще/сложнее.}
```
Если новый вывод противоречит принятому ADR — **не переопределять молча**, а явно указать: «противоречит ADR-XXXX, стоит переоткрыть потому что…».

## 8. Документы-спутники (кто за что отвечает)

| Файл | Роль | Кто обновляет |
|---|---|---|
| `CLAUDE.md` (корень) | Обзор, стек, стиль, маршрутизация знаний | при общих изменениях |
| `{область}/CLAUDE.md` | Паттерны, баги, gotchas области | после каждой правки в области |
| `CONTEXT.md` | Глоссарий домена области | при новом термине |
| `CONTEXT-MAP.md` | Указатель контекстов и их связи | при новой области |
| `docs/adr/` | Архитектурные решения | при значимом выборе |
| `docs/ARCHITECTURE.md` | Высокоуровневая схема | при смене архитектуры |
| `SKILLS.md` | Шпаргалка доступных команд/скиллов | при добавлении скилла |

## 9. Стиль работы

- **Общение** с пользователем: {язык, тон — напр. «на русском, неформально, коротко»}.
- **Код без комментариев «что делает функция»** — имена должны говорить сами.
- **Выбор технологий** — под аудиторию проекта: {напр. региональные сервисы вместо глобальных, если так требует аудитория/законы}.
- **Git:** коммитить/пушить только по просьбе. Стейджить **конкретные файлы по имени**, не `git add -A` (иначе в коммит попадёт лишнее — скелеты, артефакты). Ветка перед работой, если на дефолтной. Формат сообщений: {ваш стандарт, напр. Conventional Commits}.
- **Секреты только на сервере** — ключи внешних API никогда не уходят на клиент и не попадают в публичные `*_PUBLIC_*` переменные.
