# ADR-0003: «Липкая» маршрутизация поверх BFS

Status: accepted
Date: 2026-09-12

## Context
ТЗ: «команда самостоятельно выбирает способ поиска и обновления маршрутов», критерий — «поиск и обновление допустимых маршрутов, обработка разрывов». Чистый BFS на каждом шаге даёт кратчайший по хопам путь, но при равных длинах выбирает произвольный — маршрут «прыгал» почти каждый шаг, и показатель переключений (≈700/сутки) ничего не значил.

Рассмотрено: (а) BFS каждый шаг; (б) удерживать прежний маршрут, пока все его звенья существуют, иначе BFS; (в) Дейкстра по длине в км.

## Decision
Вариант (б): `findRoute(s, snap, clientId, prevRoute)` возвращает прежний путь с флагом `kept`, если клиент видит его первый аппарат, шлюз — последний, и все ISL-рёбра живы. Иначе — BFS по числу хопов. Одна и та же функция в сцене и в `computeAvailability`.

## Consequences
- Переключения считаются только при реальном разрыве (≈340–450/сутки при полной группировке — это уже физика движения, а не артефакт).
- Удержанный маршрут может быть на хоп длиннее свежего кратчайшего; задержка считается по фактическому пути.
- Вариант (в) остаётся кандидатом как «стратегия минимальной задержки» для сравнения стратегий (необязательный пункт ТЗ).
