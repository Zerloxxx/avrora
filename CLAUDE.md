# «Аврора» — сервис проектирования устойчивой спутниковой группировки

> Корневой файл проекта: агент читает его первым. Общее — здесь; детали по областям — в `web/CLAUDE.md`, глоссарий — в `CONTEXT.md`, решения — в `docs/adr/`.

---

## 1. О проекте

**Что строим:** веб-сервис, в котором инженер-проектировщик собирает группировку из 48 спутников (550 км, 3 плоскости), моделирует отказы аппаратов и проверяет, что каждый северный наземный пункт достигает шлюза в Мурманске не менее 90% времени. Ключевая ценность — не «показать спутники», а обосновать конфигурацию цифрами: доступность, перерывы, уязвимости, сравнение вариантов.

**Контекст:** КосмоХакатон 2026 (федеральный проект «Кадры для космоса»), кейс «Проектирование устойчивой спутниковой группировки». Сдаётся: ссылка на работающий сервис, репозиторий с инструкцией запуска, презентация (защита до 5 минут). Жюри во время проверки загружает свой JSON того же формата и меняет параметры через интерфейс.

**Дедлайн:** {УТОЧНИТЬ у организаторов — вписать абсолютную дату защиты}.

**Целевая аудитория:** инженер-проектировщик группировки и эксперты жюри (отраслевые — 50 баллов за проектные решения/устойчивость/обоснованность/удобство; технические — 50 баллов за корректность расчётов, маршрутизацию, работу с данными, качество кода и документацию). Пользователь не программист: параметры правятся в формах, ошибки в файле объясняются словами.

**Боли, которые закрываем:**
1. Наличие спутника над пунктом ≠ связь → считаем сквозной маршрут «пункт → спутники → шлюз» на каждом шаге и показываем причину, когда его нет.
2. Конфигурации нужно сопоставлять на одном периоде → сохранённые варианты и таблица сравнения с дельтами и рекомендацией.
3. Ранние этапы развёртывания и отказы ломают сеть → план по этапам, матрица N-1/N-2, Монте-Карло, резервный аппарат, второй шлюз.
4. Рекомендации должны опираться на расчёт → отчёт «Обоснование конфигурации» генерируется из результатов.

**НЕ входит в текущий этап (scope guard):**
- бэкенд и база данных — всё считается в браузере (см. ADR-0001);
- нативные мобильные приложения — вместо них вид абонента сделан второй страницей того же сайта,
  которая ставится на экран «Домой» в Safari (ADR-0008: за платформу баллов не дают, а цена высокая);
- энергетика, радиолинии, пропускная способность каналов — модель геометрическая, как в `geometry.py`;
- реальные эфемериды/TLE, возмущения орбит — круговые орбиты по формулам кейса;
- дифракция/отражения у зданий — рельеф и застройка учитываются только как геометрическая маска горизонта (ADR-0007).

## 2. Стек и архитектура

**Принципы (что незыблемо):**
- Расчётное ядро (`web/src/sim.js`) — чистые функции без DOM; оно же работает в воркере и в тестах. Формулы совпадают с `Расчетный модуль/geometry.py`; расхождение — баг.
- Интерфейс не считает: модель (`model.js`) меняет `state` и публикует события, представления только рисуют.
- Всё, что дольше ~50 мс, — в Web Worker с прогрессом; сцена не должна замирать.
- Сайт — статика без сборки: открывается любым HTTP-сервером, зависимости лежат в `web/vendor/`, интернет для показа не нужен.
- Формат данных — схема кейса `cosmo-A-1.0` плюс необязательные расширения (ADR-0007: маска горизонта пункта, наклонение плоскости, любое число очередей, `sun_eci`, `eclipse_isl_off`); файл жюри читается и выгружается без изменений.

**Стек по слоям:**
| Слой | Технологии | Хостинг |
|---|---|---|
| Backend | нет — расчёт в браузере (ES-модули + Web Worker) | — |
| Web | HTML/CSS/JS без фреймворков, Three.js r160 (3D), Canvas 2D (оверлей, диаграммы) | статика: `python3 tools/serve.py` локально; публично — GitHub Pages, https://zerloxxx.github.io/avrora/ (деплой из `main`, корень сайта = `web/`) |
| Mobile | нет нативных; вид абонента — `web/abonent/` (PWA: манифест, apple-touch-icon, service worker для офлайна) | та же статика |
| Данные / кеш | сценарии кейса, встроенные в `web/data/scenarios.js`; варианты — `localStorage` | браузер |
| Внешние сервисы | Google Fonts (есть системный fallback) | — |

**Высокоуровневая схема:** `docs/ARCHITECTURE.md`.

## 4. Порядок сборки продукта

1. Расчётное ядро: порт `geometry.py`, маршрут, доступность за сутки, валидация файла — **сделано, покрыто тестами**.
2. Сцена и базовый интерфейс: сценарии, этап, пункт, таймлайн — сделано.
3. Редактирование конфигурации, варианты, сравнение, выгрузка/загрузка — сделано (обязательные пункты ТЗ закрыты).
4. Аналитика: покрытие, развёртывание, устойчивость, качество, отчёт — сделано.
5. По замечаниям организатора: рельеф/застройка (маска горизонта), конструктор группировки (Walker, наклонение на плоскость, произвольные очереди), подбор проекта — сделано (ADR-0007).
6. Вид абонента (`web/abonent/`) и синхронизация двух видов — сделано (ADR-0008, ADR-0009).
7. Устранение недочётов по критериям оценки — сделано: полный список ошибок валидации, отпечаток конфигурации
   по содержимому, защита отчёта от устаревших результатов, сравнение стратегий маршрутизации, анализ резервных
   путей, разбивка отказов по направлениям связи, вердикт сравнения вариантов (детали — в `web/CLAUDE.md`).
8. Хостинг: GitHub Pages включён, `.github/workflows/main.yml` публикует `web/` при пуше в `main`;
   ссылка для жюри — https://zerloxxx.github.io/avrora/. Осталось: **презентация** (делает пользователь).
9. Если останется время: glTF-модель реального аппарата, ускорение N-2 (разделение геометрии сетки и маски отказов).

**Что первично:** ядро ведущее — любая новая функция сначала появляется как чистая функция в `sim.js` с тестом, потом получает интерфейс.

## 5. Глубина рассуждений — сколько думать перед действием

Не думать одинаково над всем. Уровень усилий выбирается по цене ошибки и обратимости:

| Класс задачи | Как действовать | Планирование |
|---|---|---|
| **Тривиальное** (опечатка, переименование, правка строки, известный паттерн) | Сразу делаю, без прелюдий | Не нужно |
| **Локальная фича / понятный баг** | Коротко проверяю окружение (как сделано рядом) → делаю | План в голове; TODO-список если >3 шагов |
| **Фича на несколько файлов / новый модуль / затрагивает API-контракт** | Сначала план, потом код. Читаю смежный код и `CONTEXT.md` перед стартом | Явный план + TODO-лист |
| **Архитектурное решение / необратимое / много вариантов** | Проектирую дважды: минимум 2 подхода, выбираю с обоснованием. Спорное — фиксирую в ADR | План-режим, при неясности — вопрос пользователю |
| **Диагностика неочевидного бага** | Гипотезы → проверка каждой → фикс. Не гадать, не «менять наугад» | Цикл гипотеза→эксперимент→вывод |

**Правила поверх таблицы:**
- **Есть достаточно данных — действую.** Не пересказываю варианты, которые не буду делать, не переспрашиваю то, что видно в коде.
- **Спрашиваю только то, что реально решает пользователь** — развилки в требованиях, а не выбор с очевидным дефолтом. Выбор с дефолтом — беру дефолт, называю его, иду дальше.
- **Необратимое и внешнее — подтверждаю до, а не после.** Удаление, перезапись, публикация, отправка наружу, деструктивный git. Разрешение в одном месте не переносится на следующее.
- **Перед удалением/перезаписью смотрю на цель.** Если содержимое противоречит тому, как его описали, — сообщаю, а не выполняю.
- **Не изобретаю преждевременных абстракций.** Обобщаю на третьем повторении, не на первом.

## 6. Как агент ведёт работу

- **Читаю перед тем как писать.** Перед работой в области — `CONTEXT.md` (глоссарий), `web/CLAUDE.md` и релевантные ADR. Файлов нет — молча продолжаю.
- **Многошаговое — через TODO-лист**: в работе один пункт за раз, отмечаю выполненным сразу по факту.
- **Пишу код в стиле окружения:** имена, идиомы, плотность комментариев — как в соседних файлах.
- **Проверяю результат, а не только «скомпилировалось».** Изменение ядра → `node --test`; изменение интерфейса → прогон сценария в браузере (открыть проект, изменить параметр, увидеть пересчёт).
- **Отчитываюсь честно.** Тесты упали — говорю прямо с выводом. Шаг пропустил — говорю. Сделано и проверено — говорю без хеджирования.
- **Использую специализированные сценарии (скиллы) вместо импровизации**, когда задача под них подходит (см. `SKILLS.md`).

## 7. Как и куда записывать знания (обязательно)

Цель — чтобы знание из разговора не терялось и следующий агент не переоткрывал его заново.

**Правило маршрутизации — куда сохранять новое знание:**
| Что появилось | Куда пишем |
|---|---|
| Новый доменный термин | `CONTEXT.md` (формат — раздел 7.1) |
| Паттерн / баг+фикс / gotcha / решение по коду | `web/CLAUDE.md` |
| Архитектурное решение с альтернативами и последствиями | новый файл в `docs/adr/` |
| Общее для всего проекта (стек, стиль, дедлайны, порядок работы) | этот файл |
| Новая функция, изменившееся число в демо, новый способ запуска | корневой `README.md` (он же — то, что читает жюри) |

**Когда писать:** сразу после каждой новой фичи, изменения поведения, найденного бага/решения или важного паттерна — не откладывать и не ждать отдельной просьбы.

**Как писать, чтобы дока не расходилась с кодом:**
- Правка меняет уже описанное поведение → править/удалять старый текст, а не дописывать рядом.
- В корневом `CLAUDE.md` детали не дублировать — достаточно упомянуть, что фича реализована, детали живут в `web/CLAUDE.md`.
- Формулировать конкретно: не «поправил сборку», а «X падает потому что Y; фикс — Z».
- Пишу только то, что **не** выводится из кода/git.

### 7.1. Формат CONTEXT.md (глоссарий домена)

```md
# {Название области}

{Одно-два предложения: что это за область и зачем.}

## Language

**{Термин}**:
{Что это ЕСТЬ, одно-два предложения. Не что делает — чем является.}
_Avoid_: {синонимы, которые НЕ используем}
```
Правила: быть категоричным (один термин на концепт, остальные в `_Avoid_`); только термины, специфичные для домена; определения короткие.

### 7.2. Формат ADR (архитектурное решение)

```md
# ADR-{NNNN}: {Заголовок решения}

Status: {proposed | accepted | superseded by ADR-XXXX}
Date: {YYYY-MM-DD}

## Context
## Decision
## Consequences
```
Если новый вывод противоречит принятому ADR — не переопределять молча, а явно указать: «противоречит ADR-XXXX, стоит переоткрыть потому что…».

## 9. Стиль работы

- **Общение** с пользователем: на русском, неформально, коротко, без воды; цифры важнее прилагательных.
- **Код:** ES-модули, без сборщика и без фреймворков; комментарии — по-русски, только там, где имя не объясняет «почему». Формулы и константы ядра — именами как в `geometry.py` (`R`, `MU`, `OMEGA`, `raan_deg`, `phase_deg`).
- **Интерфейс:** шрифты Unbounded + Golos Text; инженерный вид — тёмный «космос», вид абонента — тёплый графит «полярная ночь» с той же логикой цвета; русские подписи; числа — с единицами (`мин`, `мс`, `км`, `%`); цветом выделяются только смысл (маршрут — золотой, отказ — красный, шлюз — пунктир), остальное нейтральное.
- **Выбор технологий** — под жюри: всё должно открываться в браузере без установки, работать офлайн и без аккаунтов.
- **Git:** `origin` — https://github.com/Zerloxxx/avrora (общий с автором ветки `Zerloxxx`); коммитить/пушить только по просьбе,
  стейджить конкретные файлы по имени, уважать `.gitignore`. Формат сообщений: Conventional Commits (`feat:`, `fix:`, `docs:`).
  **Пуш в `main` = публикация:** workflow `on: push` без фильтра ветки задеплоит на Pages всё, что прилетело, — значит
  в `main` попадает только проверенное (тесты зелёные + прогнан демо-сценарий), а работа идёт в ветках.
- **Секреты:** в проекте их нет и не должно появиться — никаких ключей во фронтенде.
- **Репозиторий для жюри — отдельный, чистый.** `.gitignore` исключает все `.md` кроме корневого
  `README.md` (правило `!/README.md` со слешем — иначе исключение поймало бы и `web/README.md`),
  а также `.claude/` и PDF кейса. Рабочие заметки (`CLAUDE.md`, `CONTEXT.md`, `SKILLS.md`,
  `docs/`) остаются только в этом репозитории: они уже отслеживаются git, поэтому правило на них
  не влияет, но в новый клон и в выгрузку для жюри они не попадают. Выгрузка собирается копией
  дерева в отдельную папку + `git init`, чтобы история рабочих файлов не уехала жюри;
  публичный репозиторий кейса — https://gitverse.ru/hackrus.experts/kosmo-nizni_lit_64,
  ветка `master`. Всё описание сервиса при этом обязано быть в `README.md`: он единственный
  документ, который видит жюри, и ссылок на другие `.md` в нём быть не должно.
