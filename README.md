## 1. Что это и зачем

Планируется группировка из 48 спутников на круговых орбитах 550 км, выводимая тремя очередями по 16 аппаратов
с интервалом три месяца. Она должна связать северные наземные пункты со шлюзом выхода в наземную сеть
(в кейсе — Мурманск). Целевой ориентир — **сквозная доступность не ниже 90% расчётного времени для каждого пункта**.

«Аврора» — рабочее место инженера-проектировщика этой группировки. Главная идея сервиса:

> **Показать спутники — мало. Решение надо обосновать цифрами.**

Поэтому центр сервиса — не 3D-картинка (хотя она есть и честная), а связка
«параметр → пересчёт за сутки → показатель → вывод в отчёте». Любую рекомендацию, которую сервис выдаёт,
можно проследить до конкретного расчёта: какой инструмент его дал, на какой конфигурации и на какой сетке времени.

Ключевое отличие от «карты покрытия»: **наличие спутника над пунктом ещё не означает связь.**
Нужен сквозной маршрут «пункт → спутник → … → спутник → шлюз». Сервис считает именно его, на каждом шаге сетки,
и когда маршрута нет — называет причину из четырёх возможных.

## 2. Быстрый старт

### Что нужно установить

**Жюри — ничего.** Сервис открывается по ссылке в любом современном браузере: ни установки, ни регистрации,
ни расширений. Весь расчёт идёт в самом браузере, поэтому сервер не может «лежать» или «спать».

Если хочется запустить из исходников — нужен только **Python 3** как статический файловый сервер
(любой другой тоже подойдёт). Всё остальное опционально:

| Что | Зачем | Обязательно? | Как проверить, что уже есть |
|---|---|---|---|
| Браузер (Chrome, Safari, Edge, Firefox) | открыть сервис | да | — |
| **Python 3** | локальный HTTP-сервер (`tools/serve.py`) | для локального запуска | `python3 --version` (Windows: `python --version`) |
| **Node.js ≥ 18** | прогнать тесты ядра (`node --test`) | нет, только для проверки расчётов | `node --version` |
| **NumPy** (`python3 -m pip install numpy`) | сверка с эталонным `geometry.py` организаторов | нет, только для `tools/parity.mjs` | `python3 -c "import numpy"` |
| git | клонировать репозиторий | нет — исходники можно скачать архивом со страницы репозитория | `git --version` |

Чего **не** нужно ни при каком сценарии: `npm install`, сборка, `node_modules`, Docker, база данных,
ключи API, аккаунты, интернет во время показа. В проекте нет `package.json` — зависимостей нет совсем,
Three.js и текстуры Земли лежат в репозитории (`web/vendor/`, 8 МБ).

**По платформам:**

- **macOS** — Python 3 уже стоит. Команда называется именно `python3`: бинарника `python` в системе нет.
- **Linux** — Python 3 почти всегда уже стоит (`python3`).
- **Windows** — Python может отсутствовать: поставить с python.org (галочка «Add Python to PATH»)
  и запускать через `python`, а **не** `python3` — `python3` там заглушка Microsoft Store,
  она падает с кодом 9009. Или просто двойной клик на `web\start.bat`.


### Вариант 1 — просто открыть ссылку (для жюри)

**https://zerloxxx.github.io/avrora/** → кнопка «Открыть проект».

Ничего устанавливать не нужно. Сайт статический, раздаётся GitHub Pages, доступен всё время проверки.
Вид абонента — https://zerloxxx.github.io/avrora/abonent/ (или пункт «Вид абонента» в шапке).

### Вариант 2 — локально, из исходников

Нужен только Python 3 (для HTTP-сервера) — никаких `npm install`, сборки, зависимостей.

```bash
git clone https://gitverse.ru/hackrus.experts/kosmo-nizni_lit_64.git
cd kosmo-nizni_lit_64/web
python3 tools/serve.py
```

Без git — скачать архив со страницы репозитория, распаковать, и та же команда в папке `web`.

- http://localhost:8765 — **инженерный вид**;
- http://localhost:8765/abonent/ — **вид абонента**.

Вместо `serve.py` подойдёт любой статический сервер:

```bash
python3 -m http.server 8765 --directory web
```

…а также `web/start.sh` (macOS, Linux) и `web/start.bat` (Windows) — они сами откроют браузер.

> **Почему `tools/serve.py`, а не обычный `http.server`.** Он добавляет `Cache-Control: no-store`.
> Без этого браузер кеширует ES-модули: после правки `src/*.js` страница грузит прежнюю версию модуля
> и падает с «does not provide an export named …», хотя код уже верный. Для разработки это критично,
> для показа — нет (хостинг отдаёт нормальные ETag).

> **`file://` не работает** — сервису нужны ES-модули и Web Worker, им требуется HTTP-origin.
> На macOS бинарника `python` нет, только `python3`; на Windows наоборот — работает `python`.

## 4. Наша идея: четыре боли и четыре ответа

Сервис построен вокруг четырёх проблем, названных в постановке задачи. Для каждой — конкретный механизм, а не «экран».

### Боль 1. Наличие спутника над пунктом ≠ связь

Покрытие и достижимость — разные вещи. Аппарат может быть в зоне видимости, но не иметь пути до шлюза:
цепочка ISL разорвана, или последний аппарат не виден со шлюза, или шлюз сам недоступен.

**Ответ.** Сквозной маршрут считается на **каждом** из 720 отсчётов суток, отдельно по каждому пункту.
Показатель «видимость» и показатель «доступность» показаны рядом — и расхождение между ними сразу видно.
На полной группировке для C65 это 97.8% видимости против 96.7% доступности; на сценарии с ISL 2000 км —
97.8% против 77.5%: видимость почти не изменилась, связь рухнула. Когда маршрута нет, сервис называет причину:

| Причина | Код | Что это значит для проектировщика |
|---|---|---|
| нет видимого спутника над пунктом | `no_sat` | проблема покрытия — нужно больше аппаратов или другая геометрия |
| разрыв межспутниковой сети | `net_split` | проблема ISL — нужна дальность или более плотная сетка |
| нет контакта со шлюзом | `no_gw_contact` | проблема наземной инфраструктуры — нужен второй шлюз |
| шлюз недоступен | `gw_offline` | заданный период недоступности шлюза |

Эта классификация — не косметика: она прямо указывает, какое проектное решение поможет.
На `04_link_range` у C70 263 отсчёта из 720 — `net_split`, и ответ «добавить шлюз» там не сработает.

### Боль 2. Конфигурации нужно сопоставлять на одном периоде расчёта

**Ответ.** Вариант — это снимок всей конфигурации плюс сводка её показателей плюс описание отличий от исходного файла.
Окно «Сравнение вариантов» показывает **сначала вердикт** («кого брать, насколько он лучше второго и чем за это платим»),
потом таблицу: изменённые параметры подсвечены, показатели по пунктам с дельтами к первому столбцу.

Отдельно — **проверка сопоставимости**: если у вариантов разные `horizon_s`/`step_s` или разные исходные сценарии,
таблица помечается предупреждением. Кейс требует сравнивать «на одном периоде расчёта» —
дельты между разными сетками времени недействительны, и сервис об этом говорит, а не делает вид, что всё нормально.

### Боль 3. Ранние этапы развёртывания и отказы ломают сеть

**Ответ.** Пять инструментов, все считаются в Web Worker с прогрессом:

- **план развёртывания** по этапам с привязкой к месяцам;
- **сравнение раскладок очередей** — «плоскость за плоскостью» против «вперемешку» и Walker-альтернатив;
- **матрица N-1 / N-2** — полный перебор одиночных и парных отказов, запас прочности;
- **Монте-Карло** случайных отказов — вероятность удержать цель;
- **поиск слота для резервного аппарата**.

Главный вывод этого блока для кейса: раскладка очередей важнее их размера.
Первая очередь «плоскость за плоскостью» даёт худшему пункту 12.6% и перерыв 13 часов;
та же группировка с очередями «вперемешку» — 30.6% и перерыв 72 минуты. Одни и те же 16 аппаратов.

### Боль 4. Рекомендации должны опираться на расчёт

**Ответ.** Отчёт «Обоснование конфигурации» (HTML, печатается в PDF) собирается из результатов инструментов,
а не из шаблонных фраз. И главное — **отчёт отказывается цитировать устаревшие расчёты**.

У каждого результата аналитики хранится отпечаток конфигурации (FNV-1a по содержимому сценария).
При формировании отчёта отпечаток сверяется; несовпавшие инструменты в выводы не попадают, а перечисляются
отдельной строкой «Не включено в выводы: … — эти расчёты выполнялись для другой конфигурации».
В интерфейсе такие результаты помечаются плашкой «устарело».

Без этого отчёт мог бы обосновывать текущую конфигурацию цифрами N-2, посчитанными для прежней —
и жюри ловит это одним кликом.

## 5. Что умеет сервис — полный каталог

### 5.1. Сцена и время

- **Земля** — текстуры NASA Blue Marble (день 4096 px, облака, ночные огни, карта высот, блики океана),
  атмосферный обод, звёздное небо. Солнце физически согласовано с моделью: терминатор и ночные огни
  движутся вместе с временем модели.
- **Аппараты** — процедурная модель (корпус в ЭВТИ, панели, тарелка в надир). Подставить реальный glTF:
  положить файл в `web/vendor/satellite.glb`, он подхватится и отмасштабируется сам.
- **Линии**: орбиты по плоскостям (свой цвет у каждой), ISL-связи, маршрут — золотой,
  отказавшие аппараты — красный крест, шлюз — жёлтый пунктир, аппараты, закрытые рельефом, — красный пунктир.
  Аппараты в тени Земли приглушены.
- **Навигация**: вращение мышью/пальцем, зум колесом, кнопками или щипком — от крупного плана аппарата
  до всей планеты. Наведение на спутник даёт тултип с id, плоскостью и состоянием.
- **Таймлайн**: перемотка по сетке расчёта, пауза, скорости ×1 / ×4 / ×16, кнопка «перейти к текущему UTC».
  Время всегда привязывается к сетке перед снимком — картинка и диаграмма не могут разойтись.

### 5.2. Конфигурация и проектирование

| Что | Как |
|---|---|
| Сценарий из кейса | четыре кнопки; загруженный файл жюри становится пятым |
| Этап развёртывания | сегментные кнопки — их столько, сколько очередей в файле (не зашито «три») |
| Пункт для расчёта | сегментные кнопки по клиентским пунктам |
| RAAN, фазирование, наклонение каждой плоскости | таблица плоскостей, правка в полях, пересчёт через 120 мс |
| Конструктор группировки | Walker T/P/F: T аппаратов в P плоскостях, F — межплоскостное фазирование, веер RAAN 180° (Star) или 360° (Delta), своё наклонение, любое число очередей и две раскладки («очередь = плоскость» / «вперемешку»). Кейс воспроизводится как 48/3/1, веер 180° — это закреплено тестом |
| Периоды недоступности | форма «аппарат или шлюз + с… до…»; клик по спутнику на сцене выбирает его |
| Наземные пункты | добавление из списка городов, по координатам или кликом по Земле; удаление; роль клиент/шлюз |
| Рельеф и застройка вокруг антенны | пресеты местности, реальный рельеф DEM, своя маска (см. 6.3) |
| Сброс | «сбросить всё» возвращает исходный файл |

### 5.3. Показатели по каждому пункту

Считаются на полной сетке 720 отсчётов, обновляются при любой правке:

- доля времени с видимым активным спутником (**видимость**);
- доля времени со сквозным маршрутом (**доступность**) — основной показатель, сверяется с целью 90%;
- **максимальный перерыв**, минуты, и **число перерывов**;
- **среднее число переходов** маршрута (рёбер, включая две наземные линии — определение из «Описания данных»);
- **задержка** сигнала, средняя и максимальная, мс;
- **переключения маршрута** за сутки;
- **диаграмма** связи/перерывов на сутки и ближайшее окно связи;
- разбивка перерывов **по причинам**.

### 5.4. Аналитика (окно «Аналитика», шесть вкладок)

**Проект** — подбор проекта: перебор Walker-конфигураций (по умолчанию 206 вариантов, ~4 с в фоновом воркере на грубой сетке).
Выдаёт минимальную группировку, достигающую цели, фронт «число аппаратов ↔ доступность худшего пункта»,
показатели первой очереди. Кнопка «Применить» собирает выбранную конфигурацию одним кликом.

**Покрытие** — карта доступности для сетки точек 55–85° с.ш. (13 × 72 = 936 точек), наложение на глобус,
доля площади с доступностью ≥ цели. Для полной группировки — 68.3% площади.

**Развёртывание** — план по этапам с привязкой к месяцам; сравнение раскладок очередей;
жадный подбор состава очередей.

**Устойчивость** — матрица N-1 / N-2 и запас прочности; «где нужен резерв»; Монте-Карло;
**резервные пути**. Для каждого отказа видно, **какие направления связи затронуты** и какой пункт страдает сильнее.

**Качество связи** — задержка, переключения, геометрическая видимость; режим «аппараты в тени не ретранслируют»;
**сравнение стратегий маршрутизации**.

**Отчёт** — «Обоснование конфигурации»: параметры, таблица плоскостей, таблица пунктов с закрытием горизонта,
изменения относительно файла, периоды недоступности, показатели по пунктам с диаграммами,
таблица сохранённых вариантов, выводы из всех запущенных инструментов, раздел «Метод» и явный список
исключённых устаревших расчётов. Открывается отдельной страницей, печатается в PDF.

## 6. Как считает: расчётная модель

Всё ядро — `web/src/sim.js`: **чистые функции, ни DOM, ни состояния.** Тот же файл работает
в интерфейсе, в Web Worker и в `node --test`. Формулы и имена константант совпадают с эталонным
`Расчетный модуль/geometry.py` от организаторов — расхождение считается багом и ловится тестами.

### 6.1. Константы и положение аппарата

```
R = 6371.0 км                     радиус Земли
MU = 398600.435507 км³/с²         гравитационный параметр
T_земли = 86164.09054 с           период вращения → OMEGA = 2π/T
c = 299792.458 км/с               скорость света (для задержки)

r = R + altitude_km               радиус орбиты
n = sqrt(MU / r³)                 угловая скорость
u(t) = slot_deg + phase_deg + n·t аргумент широты
```

Инерциальные координаты (Ω — RAAN плоскости, i — наклонение):

```
x = r·(cos Ω·cos u − sin Ω·sin u·cos i)
y = r·(sin Ω·cos u + cos Ω·sin u·cos i)
z = r·sin u·sin i
```

Переход к связанной с Землёй системе, θ = earth_angle0 + 2πt/T:

```
xe =  cos θ·x + sin θ·y
ye = −sin θ·x + cos θ·y
ze =  z
```

**Расширение сверх кейса:** наклонение берётся у плоскости (`planes[].inclination_deg`), если задано,
иначе общее из `environment` — это позволяет проектировать группировки с «разными осями».

### 6.2. Сетка времени

```
timeGrid(s) → отсчёты 0, 120, 240, …, 86 280 с — ровно 720 штук
```

Правый конец **не включается** — так определено в «Описании данных». Каждый отсчёт представляет интервал
длиной `step_s`. Вся статистика считается только на этой сетке; сцена привязывает время к сетке перед снимком,
поэтому картинка, диаграмма и выгрузка `routes` не могут разойтись.

Грубая сетка (`stepMul`) используется **только внутри переборов** (оптимизаторы, N-2, Монте-Карло, покрытие).
Всё, что показывается пользователю как итог, считается на полной сетке.

> Ошибка «+1 отсчёт» (721 вместо 720) у нас уже была — проценты плыли на 0.1 п.п. относительно эталона.
> Теперь сетка только через `timeGrid()`, и это закреплено тестом.

### 6.3. Видимость с пункта

Координаты пункта: `g = R·(cos φ·cos λ, cos φ·sin λ, sin φ)`.
Угол возвышения: `arcsin(((s − g)·g) / (‖s − g‖·R))`.

**Правило кейса:** контакт возможен, если возвышение ≥ `min_elevation_deg` (10°) и аппарат активен.

**Расширение сверх кейса (ADR-0007): маска горизонта.** У пункта может быть `horizon_mask` —
массив углов закрытия неба по секторам азимута (36 секторов по 10°, от севера по часовой).
Тогда условие становится `возвышение ≥ max(min_elevation_deg, mask[сектор азимута])`.
Закрытые аппараты не исчезают — они помечаются флагом `blocked` и рисуются красным пунктиром:
для жителя «спутника нет» и «спутник за сопкой» — разные ответы (первое — ждать пролёта, второе — переставить антенну).

Три источника маски:

| Источник | Как получается |
|---|---|
| Пресет местности | открытая тундра, посёлок (дома 8 м в 40 м), город (16 м в 50 м), плотный город (30 м в 60 м), горная долина (хребет 25° с юга), антенна на крыше — через `buildingAngle(h, d)` |
| Реальный рельеф DEM | предрасчёт `tools/horizon-mask.py` по ASTER GDEM 30 м (OpenTopoData) → `data/terrain.js` для пунктов кейса и городов; из браузера — кнопка «запросить рельеф» по Copernicus DEM GLO-90 (open-meteo) |
| Своя | произвольный массив углов |

Формула одна — `maskFromProfiles()`; скрипт её дублирует, и расхождение считается багом.
Маска из нулей даёт результат, в точности совпадающий с правилом кейса — это тест.

Почему два источника DEM: OpenTopoData не отдаёт CORS, из браузера его не вызвать.

### 6.4. Межспутниковая связь (ISL)

Ребро между двумя активными аппаратами существует, если:

1. `‖b − a‖ < isl_range_km`;
2. отрезок не пересекает Землю. Проверка как в кейсе: `d = b − a`, `q = clip(−a·d / d·d, 0, 1)`,
   ближайшая к центру точка `a + q·d` должна быть дальше R от центра.

Связи двунаправленные. Недоступный аппарат сохраняет расчётное положение, но исключается из связей.

**Необязательный режим:** `eclipse_isl_off` — аппарат в цилиндрической тени Земли
(относительно `environment.sun_eci`) не ретранслирует. Переключается чекбоксом в «Качестве связи».

### 6.5. Снимок сети

```js
snapshot(scenario, t) → {
  t, pos,            // положения всех аппаратов
  active, failed,    // launch_batch ≤ launch_stage и не в отказе
  adj, isl,          // граф ISL: списки смежности и список рёбер
  ground: {          // по каждому наземному пункту:
    [id]: { pos, offline, visible, visibleRaw, blocked }
  },
  eclipsed
}
```

Это единственный источник истины о состоянии сети: и сцена, и все метрики, и вид абонента
читают сеть только отсюда.

### 6.6. Показатели

| Показатель | Определение |
|---|---|
| Видимость | отсчёты с ≥1 видимым активным аппаратом / всего отсчётов |
| Доступность | отсчёты со сквозным маршрутом / всего отсчётов |
| Максимальный перерыв | самая длинная серия отсчётов без маршрута × `step_s` |
| Число перерывов | количество непрерывных серий без маршрута |
| Переходы | число рёбер маршрута = аппаратов + 1, включая две наземные линии; при отсутствии пути значения нет |
| Задержка | длина пути «пункт → аппараты → шлюз» / c, мс, односторонняя, без бортовой обработки |
| Переключения | смены цепочки аппаратов между соседними отсчётами |
| Оценка конфигурации | худший пункт × 1000 + средняя доступность × 100 + видимость × 10 − перерывы·0.5 − переходы·0.1 (скаляр для оптимизаторов, лексикографический по смыслу) |

### 6.7. Валидация входного файла

`validate()` — порт проверки из `geometry.py`, расширенный. Главный принцип:

> **Ни одна ошибка не прекращает проверку.** Пользователь должен увидеть весь список и починить файл за один проход.

Разделы проверяются независимо (отсутствие `environment` не мешает проверить `design`), диапазон значения —
только если само значение оказалось числом, однотипные сообщения сворачиваются с указанием числа повторов.
На битом файле раньше выводилось 2 сообщения, теперь 10.

Что проверяется: конечность всех чисел, диапазоны (высота 200…1200 км, широта, долгота, RAAN, фаза),
уникальность id в каждом списке и различность id спутников и пунктов, разрешимость ссылок
`satellites[].plane_id` → `planes[].id` и `failures[].satellite_id` → `satellites[].id`,
целость и положительность `horizon_s`/`step_s` и кратность горизонта шагу, нахождение всех интервалов
недоступности внутри периода расчёта с положительной длительностью, наличие хотя бы одного шлюза и клиента.
Необязательные поля проверяются только если они есть.

### 6.8. Скорость расчёта

Замерено на MacBook (Node 24; в браузере порядок тот же). Всё, что дольше ~50 мс, уходит
в Web Worker с прогресс-баром — сцена не замирает, и кнопка инструмента блокируется до конца расчёта.

| Операция | Время | Где считается |
|---|---|---|
| снимок сети (`snapshot`) на один момент | 0.04 мс | в кадре сцены, 60 раз в секунду |
| доступность за сутки, 48 КА × 3 пункта × 720 отсчётов | **≈40 мс** | сразу, в основном потоке |
| карта покрытия Арктики (936 точек) | 0.1 с | воркер |
| сравнение трёх стратегий маршрутизации | 0.2 с | воркер |
| резервные пути для пункта | < 0.1 с | воркер |
| сравнение раскладок очередей | 0.5 с | воркер |
| уязвимые аппараты (48 прогонов суток) | 1.6 с | воркер |
| Монте-Карло, 300 прогонов | 3.4 с | воркер |
| подбор проекта, 206 Walker-конфигураций | 3.8 с | воркер, грубая сетка |
| матрица N-1 / N-2 (все пары из 48 аппаратов) | ~14 с | воркер, грубая сетка `stepMul=3` |
| подбор RAAN и фазирования (покоординатный спуск, 2 прохода) | ~18 с | воркер, полная сетка |

Два самых долгих инструмента — единственная цена отказа от бэкенда (ADR-0001): они считаются
на машине жюри. Оба идут с прогрессом и не блокируют интерфейс; остальное ощущается мгновенным.
Именно поэтому переборы внутри используют грубую сетку, а **итоговые** показатели,
которые пользователь видит как результат, всегда считаются на полной.

## 7. Маршрутизация и её обоснование

### 7.1. Граф и базовый поиск

Маршрут ищется в графе «активные аппараты + существующие на этом шаге ISL-рёбра».
Клиентский пункт может подключиться к любому видимому с него аппарату; маршрут обязан закончиться
на аппарате, видимом с доступного шлюза. Клиентские пункты **не ретранслируют** трафик (требование кейса).
Базовый поиск — BFS по числу переходов.

### 7.2. Почему маршрут «липкий» (ADR-0003)

Чистый BFS на каждом шаге при равных длинах выбирает произвольный из кратчайших путей.
Маршрут «прыгал» почти каждый шаг, и показатель переключений (≈700/сутки) не значил ничего.

Поэтому `findRoute()` **удерживает прежний маршрут, пока живы все его звенья**
(клиент видит первый аппарат, шлюз видит последний, все ISL-рёбра на месте) — и только при разрыве ищет заново.
Та же функция используется и в сцене, и в расчёте доступности, поэтому переключения на экране и в метриках — одни и те же.

Важное свойство, закреплённое тестом: **доступность от липкости не зависит.**
Если прежний путь валиден, путь существует; если нет — BFS найдёт любой существующий.
Липкость меняет переключения, переходы и задержку, но не ответ «есть маршрут или нет».

### 7.3. Выбор алгоритма обоснован расчётом

Кейс оставляет выбор способа поиска команде — значит, выбор нужно доказать, а не объявить.
«Аналитика → Качество связи → Сравнить стратегии маршрутизации» гоняет **одни и те же сутки тремя способами**
через один и тот же код (`computeAvailability(s, stepMul, { strategy })`), поэтому колонки сравнимы.

Полная группировка, `01_full_constellation`, 720 отсчётов, 3 пункта:

| Стратегия | Доступность худшего пункта | Переключений за сутки | Ср. переходов | Ср. задержка |
|---|---|---|---|---|
| **липкий BFS** (выбран) | 96.7% | **1216** | 2.81 | 14.42 мс |
| минимум переходов (BFS заново каждый шаг) | 96.7% | 1439 | 2.70 | 13.73 мс |
| минимум задержки (Дейкстра по длине линий) | 96.7% | 1367 | 2.70 | 13.25 мс |

**Вывод, который и есть обоснование:** доступность у всех трёх **совпадает** — существование пути
определяется геометрией сети, а не алгоритмом поиска. Расходятся переключения и задержка.
Липкий BFS даёт на **223 переключения в сутки меньше**, чем поиск заново, ценой **1.2 мс** средней задержки
против стратегии минимума задержки. Для абонента каждое переключение — переустановка сессии, миллисекунда — нет.

Совпадение доступности между стратегиями проверяется тестом: расхождение означало бы баг в поиске.

### 7.4. Причина отсутствия маршрута

Когда пути нет, сервис не пишет «нет связи», а определяет причину (см. таблицу в разделе 4).
Логика: нет видимых аппаратов → `no_sat`; все шлюзы в отказе → `gw_offline`;
не достигли ни одного аппарата, видимого со шлюза → `net_split` либо `no_gw_contact`
в зависимости от того, есть ли вообще такие аппараты.

## 8. Анализ устойчивости

### 8.1. Матрица N-1 / N-2 и запас прочности

Полный перебор: каждый аппарат выводится из строя на весь горизонт (диагональ), затем каждая пара (остальные клетки).
В клетке — минимальная доступность по пунктам. Результат на полной группировке:

| | Доступность худшего пункта |
|---|---|
| без отказов | 97.1% |
| худший одиночный отказ (N-1) | 94.2% |
| худшая пара отказов (N-2) | 91.3% |
| **запас прочности** | **2** (цель 90% держится при любых двух одновременных отказах) |

> **Почему здесь 97.1%, а в таблице сценариев 96.7%.** Полный перебор всех пар из 48 аппаратов — это 1176 прогонов
> суток, поэтому он идёт на грубой сетке (`stepMul = 3`, каждый третий отсчёт): 14 секунд вместо нескольких минут.
> Базовая строка в матрице считается на той же грубой сетке, чтобы клетки были сравнимы между собой, —
> отсюда 97.1% против 96.7% на полной. Сравнивать надо внутри матрицы, а итоговый показатель пункта
> всегда берётся с полной сетки. Это общее правило сервиса: грубая сетка — только внутри переборов.

Для каждой опасной пары названо, **какой пункт** она роняет, а для каждого одиночного отказа —
по каким направлениям связи просадка и насколько. Критерий требует показать «какие направления связи затронуты»,
а не только минимум по всем пунктам.

### 8.2. Резервные пути: не «есть ли резерв», а «что именно узко»

Инструмент на каждом шаге строит маршрут, затем ищет путь **в обход всех его аппаратов** (полный независимый резерв)
и поочерёдно **в обход каждого** (незаменимые аппараты). Дальше — ключевое разделение причин:

| Показатель | Что означает | Чем лечится |
|---|---|---|
| `disjointShare` | есть полностью независимый обходной путь | — |
| `spofShare` | в маршруте есть незаменимый аппарат | см. ниже |
| `oneAccessShare` | над пунктом виден **ровно один** аппарат | покрытием: больше аппаратов, другая геометрия |
| `chainCriticalShare` | узкое звено **в середине** цепочки | дальностью ISL или вторым шлюзом |

C65 на полной группировке: независимый обход есть только **17.1%** времени со связью,
в **82.9%** в маршруте есть незаменимый аппарат — но из них **69.7%** это просто единственный аппарат
в зоне видимости, и лишь **15.9%** — тонкое звено в середине. Вывод: для C65 резервирование даёт
увеличение числа аппаратов над пунктом, а не рост дальности ISL. Без этого разделения
обе причины выглядели бы как один красный показатель «нет резерва», и решение было бы выбрано наугад.

Отдельно обработан случай, когда у пункта **вообще нет** маршрута за сутки: тогда «0% незаменимых аппаратов» —
не хорошая новость, и инструмент говорит прямо: «резервировать нечего, сначала нужна связь».

### 8.3. Остальные инструменты устойчивости

- **Уязвимые аппараты** — по очереди выводим каждый спутник на сутки, смотрим просадку худшего пункта;
  для каждого названы затронутые направления и самый страдающий пункт.
- **Где нужен резерв** — перебор свободных слотов между соседями плоскости; резервные аппараты
  получают id `SP1`, `SP2`… и добавляются в первую очередь.
- **Монте-Карло** — случайные отказы с заданной вероятностью, N прогонов, вероятность удержать цель.
  (Ограничение: `Math.random()` без сева, два прогона дают разные цифры.)
- **Второй шлюз** — добавляется кликом по Земле или из списка городов. Эффект на первой очереди:
  C65/C70/C72 = 27.2/15.8/12.6% → **34.3/44.4/56.9%** при добавлении Тикси.

## 9. Вид абонента и синхронизация двух видов

### 9.1. Зачем он есть

Показатель «96.7%» ничего не говорит человеку, который живёт в пункте C65.
Вид абонента (`web/abonent/`) переводит тот же расчёт на язык жителя: **есть ли связь сейчас,
когда появится, на сколько, через какой аппарат идёт сигнал и какие спутники над головой.**

Это **не другое приложение и не другой расчёт**: та же `sim.js`, та же сетка, тот же формат ссылки.
Числа на телефоне совпадают с таблицей инженера по построению — и это проверено тестами и сквозными прогонами
(этап 1 + отказ S05 для C72 дают 11.1% и перерыв 796 мин на обеих страницах).

### 9.2. Что показывает

- **Статус**: «Связь есть» / «Связи нет, появится в 18:38 — нет контакта со шлюзом» — с причиной словами.
- **Когда будет связь**: расписание окон связи и перерывов на сутки, встык покрывающих горизонт.
- **Через что идёт сигнал**: аппарат, наземная станция, задержка («Сигнал идёт 9 мс»).
- **Весь день**: диаграмма связи/перерывов, доля связи за сутки, самый длинный перерыв.
- **Спутники над вами**: сторона света, угол над горизонтом и **отдельно те, что закрыты рельефом** —
  с углом закрытия.
- **Где вы находитесь**: выбор пункта или «Определить моё местоположение» — фактические координаты телефона
  становятся новым клиентским пунктом, и для него считается доступность.

Палитра «полярная ночь»: тёплый графит, связь — аврора, маршрут — янтарь, отказ — коралл.
Раскладка в одну колонку: телефон в первую очередь.

### 9.3. Установка на телефон

Открыть `/abonent/` в Safari на iOS → «Поделиться» → «На экран „Домой“». Запускается без адресной строки,
со своей иконкой, **после первого открытия работает без сети** — для северного пункта офлайн основной режим,
а не украшение. Service worker разделяет стратегии: код и разметка — «сначала сеть, кеш как запас»,
неизменяемое (vendor, текстуры, шрифты) — «сначала кеш».

Почему страница, а не нативное iOS-приложение — **ADR-0008**: за платформу баллов не дают,
а цена высокая (Mac, Xcode, Apple Developer, ревью TestFlight), и «коннект с сайтом» потребовал бы бэкенда.

### 9.4. Два вида в такт (ADR-0009)

Если инженерный вид и вид абонента открыты в одном браузере, **второй идёт за первым**: время, скорость,
пауза и конфигурация. Переключили этап, задали отказ, сменили местность — статус жителя меняется сразу.
На защите это единственный способ показать причину и следствие в одном кадре.

- Связь односторонняя: инженерный вид ведёт, абонент следует. Такт `{t, playing, speed}` — 4 раза в секунду
  через `BroadcastChannel`, конфигурация (`#c=`-дифф) — по факту изменения. Ведомый доигрывает время между тактами сам,
  поэтому движение плавное на 60 кадрах при четырёх сообщениях в секунду.
- Ведомый шлёт `hello` при открытии и `alive` раз в 2 с; ведущий зажигает точку у пункта «Вид абонента» в шапке —
  докладчик видит, что связь есть.
- **Ручное действие сильнее такта**: кнопка «Сейчас» отцепляет житель от ведущего (`detached`),
  «За инженером» возвращает. Выбранный пункт принадлежит жителю, а не ведущему.
- Подпись под часами всегда говорит, какой из трёх режимов активен: «за инженерным видом, ×16» /
  «инженерный вид в фоне, ×16» / «сейчас, UTC» / «выбранный момент».

**Почему одного канала оказалось мало.** Браузер тормозит таймеры скрытой вкладки: с 250 мс до секунды сразу
и до раза в минуту через несколько минут, а полностью перекрытую вкладку может заморозить.
Из-за этого ведомый показывал скорость на момент переключения окон — инженер включал ×16, у абонента оставался ×4.
Теперь ведущий дублирует последнее состояние в `localStorage` (`aurora.sync.last`) — раз в секунду и **сразу**
при смене скорости, паузы или момента, — а ведомый читает запись при возвращении на экран
(`visibilitychange`, `pageshow`) и доигрывает время сам. Запись старше двух минут игнорируется:
это уже не «переключился между окнами», а другая сессия.

Побочная выгода: вид абонента переживает перезагрузку страницы и закрытие инженерного окна —
продолжает с того же момента и честно пишет «инженерный вид в фоне».

**Граница решения:** работает только между окнами одного браузера на одной машине — это `BroadcastChannel`,
без сервера. Ноутбук и реальный iPhone так не связать; на отдельных устройствах оба вида и так показывают
один момент, пока идут по живому UTC. Связать их по-настоящему можно было бы только WebSocket-релеем,
то есть бэкендом — против ADR-0001.

> Для показа оба окна должны быть видимы: в фоновой вкладке браузер останавливает отрисовку.
> Данные приходят, но картинка замирает — это не баг.

## 10. Архитектура

### 10.1. Принципы (что незыблемо)

1. **Расчётное ядро — чистые функции без DOM и без состояния.** Один `sim.js` работает в интерфейсе,
   в воркере и в тестах. Формулы совпадают с `geometry.py`; расхождение — баг.
2. **Интерфейс не считает.** Модель (`model.js`) — единственное место мутаций состояния,
   она публикует события; представления только читают и рисуют.
3. **Всё, что дольше ~50 мс — в Web Worker** с прогрессом. Сцена не должна замирать.
4. **Сайт — статика без сборки.** Открывается любым HTTP-сервером, зависимости в `vendor/`,
   интернет для показа не нужен.
5. **Формат данных жюри — неприкосновенен.** Схема `cosmo-A-1.0` плюс необязательные расширения;
   файл жюри читается и выгружается без изменений.

### 10.2. Схема модулей

```
             └─ src/app.js          (точка входа: DOM-события → модель/сцена/аналитика; старт цикла)
```

### 10.4. Поток данных

1. `loadScenario(raw)` → `state.base`, `state.scenario` → `recompute()` → `computeAvailability`
   (≈40 мс на сутки, см. 6.8) → событие `recomputed` → панель «Доступность», вкладка «Качество».
2. Правка в форме → `model.setX()` → `markChanged()` → (`scene:rebuild`, если менялась геометрия)
   → через 120 мс `recompute()` + `controls`.
3. Каждый кадр: `snapshot(scenario, t)` → `findRoute(prev)` → рендер → статус.
4. Тяжёлое (оптимизаторы, матрица пар, Монте-Карло, покрытие, подбор проекта) → `runTask` → воркер →
   прогресс → результат **вместе с отпечатком конфигурации** в `state.analysis` → рендерер вкладки.
5. Сохранение варианта копирует сценарий + сводку; сравнение и отчёт читают только сохранённые данные.
6. Вид абонента: `#c=` → дифф на копию встроенного сценария → `computeAvailability` + `contactWindows`
   → статус, расписание окон, небо. Время по умолчанию — текущий UTC, а не полдень: жителю нужен ответ «когда».

### 10.6. Инварианты

- Вся физика — в `sim.js`. Проверка против `geometry.py`: на `t=0` полной группировки **76 ISL-рёбер**
  и маршрут **C65 → S20 → G_MUR** (2 перехода).
- Расчётная сетка одна — `timeGrid()`, 720 отсчётов, правый конец исключён.
- Расстояния в километрах везде. В сцене единица — радиус Земли, орбита визуально приподнята ×1.42 (ADR-0004);
  расчёты при этом идут в настоящих километрах, а рёбра берутся из снимка, не из геометрии сцены.
- Системы координат: ECEF с осью Z на север (как в `geometry.py`) ↔ Three.js с осью Y вверх:
  `toThree(p) = (p.x, p.z, −p.y)`.
- Время модели у абонента имеет три режима, и подпись под часами обязана говорить, какой активен.
- Результат аналитики всегда хранится вместе с отпечатком конфигурации, на которой посчитан.

```jsonc
}
```

Интервалы недоступности: начало включается, конец исключается. Аппарат активен, если
`launch_batch ≤ launch_stage` и он не в отказе на этот момент.

### 11.2. Наши необязательные расширения (ADR-0007)

Все игнорируются `geometry.py` без ошибок; в экспорт попадают **только если проектировщик их задал**,
поэтому файл жюри выгружается ровно таким, каким пришёл.

| Поле | Назначение |
|---|---|
| `ground_sites[].horizon_mask` | массив углов закрытия неба по секторам азимута (36 по 10°, от севера по часовой; допустимо ≥4) |
| `ground_sites[].terrain` / `terrain_source` / `h0_m` | откуда взята маска (пресет / `dem` / `custom`), источник DEM, высота точки — для отчёта |
| `design.planes[].inclination_deg` | наклонение отдельной плоскости; без поля — общее из `environment` |
| `launch_batch` | любое целое ≥ 1 (не только 1–3); `launch_stage` — от 1 до максимальной очереди |
| `environment.sun_eci` | условное направление на Солнце для расчёта тени |
| `environment.eclipse_isl_off` | аппараты в тени не ретранслируют |

Два инварианта закреплены тестами: **маска из нулей даёт результат, в точности совпадающий с правилом кейса**,
и **Walker 48/3/1 с веером 180° воспроизводит группировку кейса**. Расширения не могут незаметно сломать эталон.

### 11.3. Выход: схема `cosmo-A-result-1.0`

```jsonc
{
  "schema_version": "cosmo-A-result-1.0",
  "effective_scenario": { ... },    // полный использованный сценарий со всеми правками пользователя
  "routes": [                       // одна запись на каждую пару «отсчёт — клиентский пункт»
    { "t_s": 0,   "client_id": "C65", "path": ["C65", "S20", "G_MUR"] },
    { "t_s": 120, "client_id": "C65", "path": [], "reason": "no_sat" }
  ],
  "summary": { "C65": { "availability": 0.967, "maxGapMin": 8, ... } },
  "time_grid": { "step_s": 120, "steps": 720 }
}
```

`path` — последовательность id от пункта до шлюза; пустой список означает отсутствие маршрута
(у таких записей мы дополнительно пишем причину). Для 3 пунктов × 720 отсчётов это 2160 записей.

### 11.4. Ссылка на конфигурацию

`#c=<base64>` — дифф относительно встроенного сценария: id сценария, этап, плоскости (RAAN, фаза, наклонение),
отказы, добавленные и удалённые пункты, маски рельефа, добавленные аппараты, очереди, режим тени, выбранный пункт.
Если менялся состав группировки, кодируется весь `design`. Формат общий для обеих страниц
(`configlink.js`) — иначе они разошлись бы и по одной ссылке показали разные числа.
Для файлов, загруженных вручную, ссылка не работает (у них нет встроенной базы).

## 12. Воспроизводимые числа

Все значения ниже получены прогоном ядра на встроенных сценариях кейса,
полная сетка 720 отсчётов, шаг 120 с, цель 90%. Их можно повторить в интерфейсе.

### 12.1. Четыре сценария кейса

| Сценарий | Условия | C65 | C70 | C72 | Макс. перерыв (C65/C70/C72) | Основная причина перерывов |
|---|---|---|---|---|---|---|
| 01 Полная группировка | 48 КА, ISL 3000 | **96.7%** | **98.8%** | **98.9%** | 8 / 2 / 2 мин | нет контакта со шлюзом |
| 02 Первая очередь | 16 КА | 27.2% | 15.8% | 12.6% | 572 / 658 / 796 мин | нет видимого спутника |
| 03 Отказ 10 аппаратов | с 6-го часа | 79.3% | 80.8% | 82.5% | 24 / 24 / 20 мин | нет видимого спутника + разрывы сети |
| 04 Дальность ISL 2000 км | 48 КА | 77.5% | 62.2% | 65.1% | 94 / 178 / 4 мин | **разрыв межспутниковой сети** |

Читается это так. Полная группировка цель 90% проходит с запасом по всем трём пунктам, и без правок
её менять не нужно. Первая очередь до цели не дотягивает по физике: 16 аппаратов в одной плоскости
не могут непрерывно обслуживать три пункта. Отказ десяти аппаратов роняет связь до 79–83% —
цель теряется, но сеть не рассыпается. А ограничение ISL до 2000 км бьёт **по сети, а не по покрытию**:
видимость у C70 остаётся 99.9% при доступности 62.2%. Это тот самый разрыв между «спутник виден»
и «связь есть», вокруг которого построен сервис — и четыре сценария кейса показывают его
с четырёх разных сторон.

| Решение | Было | Стало |

## 13. Проверка корректности

Сервис считает то же, что эталонный модуль организаторов, и это проверяется двумя независимыми способами.

### 13.1. Тесты ядра

```bash
cd web && node --test
```

**39 тестов, все зелёные.** Что они покрывают:

- **сверка с эталоном**: 76 ISL-рёбер и маршрут C65 → S20 → G_MUR на `t=0` полной группировки;
  полное совпадение множества рёбер на 12:00 (если установлены Python и NumPy — тест сам запускает `geometry.py`);
- **сетка времени**: ровно 720 отсчётов, правый конец исключён;
- **доступность** по всем четырём сценариям кейса;
- **липкая маршрутизация**: маршрут удерживается, пока живы звенья (тест на `t=120→240`:
  на `0→120` S20 уходит из видимости шлюза, и тест был бы бессмысленным);
- **стратегии**: доступность у трёх стратегий совпадает; путь Дейкстры не длиннее пути BFS на том же шаге;
- **резервные пути**: независимый обход и незаменимый аппарат — взаимоисключающие состояния шага,
  `disjointShare + spofShare ≤ 1`; `routeAvoiding()` действительно обходит запрещённые аппараты;
- **валидация**: одна ошибка не скрывает остальные; однотипные сворачиваются;
  отсутствие `environment` не мешает проверить остальной файл;
- **отпечаток конфигурации**: меняется при правке `raan_deg` 120 → 130 (прежняя версия считала длину JSON
  и давала один отпечаток при разнице доступности 3.7 п.п.);
- **разбивка отказов по направлениям**: перечислены ровно те направления, у которых доступность упала;
  у каждой опасной пары назван страдающий пункт;
- **окна связи абонента**: `contactWindows().availability` совпадает с `computeAvailability()` по построению,
  окна и перерывы встык покрывают горизонт;
- **рельеф**: маска закрывает аппараты, роняет доступность и видна абоненту; маска из нулей = правило кейса;
- **конструктор**: Walker 48/3/1 веер 180° = группировка кейса; наклонение на плоскость работает.

### 13.2. Полная сверка с `geometry.py`

```bash
cd web && node tools/parity.mjs
```

Запускает эталонный модуль организаторов на **всех четырёх сценариях в пяти моментах времени**
(0, 12000, 43200, 60000, 86280 с) и сравнивает положения аппаратов, флаг активности,
множество ISL-рёбер и видимость с наземных пунктов.

**Текущий результат: расхождений нет.** Позиции совпадают до **1·10⁻¹¹ … 1·10⁻¹⁰ км** (машинная точность),
множества рёбер и наземных линий совпадают покомпонентно, флаги активности совпадают.

```
01_full_constellation  t=    0  Δpos=6.0e-12  ISL 76/76 расх=0  назем. 10/10 расх=0  active расх=0
...
04_link_range          t=86280  Δpos=9.9e-11  ISL 18/18 расх=0  назем.  6/6  расх=0  active расх=0

ВСЁ СОВПАДАЕТ с geometry.py
```

> Тонкость, на которую легко попасться: `edges` в выводе `geometry.py` — это ISL **плюс** наземные линии
> (на `t=0` полной группировки 86 = 76 ISL + 10 наземных). Сравнивать их с `snap.isl` напрямую нельзя.

### 13.3. Ручная сверка одного снимка

```bash
python3 "Расчетный модуль/geometry.py" "Данные/01_full_constellation.json" 0
```

Выводит эталонное состояние сети в нулевой момент — можно сравнить с тем, что показывает сервис.

### Публикация

Сервис — статика, поэтому публикуется любым хостингом файлов. Рабочая ссылка выложена через
**GitHub Pages**: workflow `.github/workflows/main.yml` (`on: push`) берёт папку `web/` как корень
сайта — инженерный вид на `/`, вид абонента на `/abonent/`, публикация занимает около минуты.

**Пуш в основную ветку = публикация**, поэтому туда попадает только проверенное: зелёные тесты
плюс прогон демо-сценария. Workflow без фильтра ветки — пуш любой ветки тоже деплоит.

Развернуть у себя можно чем угодно, что раздаёт файлы: хватит скопировать содержимое `web/`
на любой статический хостинг. Сборка не нужна — ни шага установки, ни зависимостей.

Чеклист перед отправкой ссылки жюри:

- [ ] `cd web && node --test` — зелёные;
- [ ] `cd web && node tools/parity.mjs` — расхождений нет;
- [ ] прогнан демо-сценарий (раздел 16);
- [ ] `web/data/scenarios.js` пересобран, если менялась папка `Данные/`;
- [ ] после деплоя открыты **обе** страницы и проверены файлы `src/*.js`
      (был случай, когда публичная ссылка отдавала старый `main`).

## 16. Демонстрация за 5 минут

### Базовые сценарии проверки из постановки задачи

Все четыре прогоняются в сервисе без подготовки:

| Сценарий кейса | Как выполняется |
|---|---|
| **Полная группировка.** Загрузить `01_full_constellation.json`, выполнить расчёт, выбрать пункт, посмотреть маршрут в нескольких моментах | «Открыть проект» → сценарий «Полная группировка» → пункт C65 → перемотка таймлайна; маршрут и причина перерыва видны в панели «Связь» |
| **Этап развёртывания.** Переключить очередь с третьей на первую, сравнить доступность и перерывы | кнопки этапов: 96.7/98.8/98.9% → 27.2/15.8/12.6%, перерыв 8 мин → 572 мин |
| **Отказ аппарата.** Выбрать спутник текущего маршрута, задать период недоступности, повторить расчёт | клик по аппарату на сцене → форма периодов недоступности → «Добавить»; маршрут перестраивается либо появляется перерыв с причиной |
| **Изменение проекта.** Изменить ориентацию или фазирование плоскости, сохранить вариант, сопоставить; выгрузить и загрузить обратно | таблица плоскостей → «Варианты → Сохранить» → «Сравнить отмеченные»; «Выгрузить → Сценарий (JSON)» → «Загрузить JSON» тот же файл |

### Сценарий защиты (последовательность кадров)

1. **Сцена** → «Открыть проект». Полная группировка, 48 аппаратов, 76 ISL-связей.
2. **Маршрут C65** и причина перерыва — маршрут золотой, причина словами.
3. **Этап 1**: 27 / 16 / 13% — первая очередь физически не может дать цель.
4. **Второй шлюз Тикси** на первой очереди: 34 / 44 / 57% — наземная инфраструктура дешевле аппаратов.
5. **«Подобрать RAAN и фазу»** на полной группировке: 96.7% → **99.9%**.
6. **Местность C65 «рельеф DEM»**: 96.7% → **68.5%** — пункт в Полярном Урале, закрытие горизонта до 36°.
   Вот настоящая доступность, а не геометрическая.
7. **«Аналитика → Развёртывание → Сравнить раскладки очередей»**: первая очередь 12.6% → 30.6%,
   перерыв 13 ч → 72 мин на тех же 16 аппаратах.
8. **«Качество связи → Сравнить стратегии маршрутизации»**: доступность одинаковая,
   липкий BFS экономит 223 переключения в сутки ценой 1.2 мс — **чем обоснован выбор алгоритма**.
9. **«Устойчивость → Резервные пути»**: у C65 независимый обход только 17% времени,
   и причина — один аппарат над пунктом, а не тонкая ISL-сеть. Разные причины — разные решения.
10. **«Проект → Подобрать»**: 48/6/3 Star даёт 99.6% на открытой местности.
11. **«Устойчивость → N-1/N-2»**: запас прочности 2.
12. **«Сформировать отчёт»** — всё вышеперечисленное выходит документом.

## 18. Архитектурные решения (ADR)

Каждое значимое решение принималось с разбором альтернатив, и здесь зафиксировано главное:
что выбрали и чем за это платим. Номера используются по всему README как короткие ссылки
(«ADR-0003» в разделе о маршрутизации — это строка 0003 в таблице ниже).

| ADR | Решение | Главное последствие |
|---|---|---|
| **0001** | Расчёт в браузере, без бэкенда | Нет сервера → нет падений во время проверки, нет секретов, ссылка живёт вечно. Цена: тяжёлые переборы идут на машине жюри; при росте до сотен аппаратов решение придётся пересматривать |
| **0002** | Ядро — чистые функции, общие для UI, воркера и тестов | Новая аналитика = функция + строка в диспетчере + рендерер; ядро тестируется без браузера. Цена: порядок перерисовки задаётся подписками, а не последовательностью кода |
| **0003** | «Липкая» маршрутизация поверх BFS | Переключения считаются только при реальном разрыве (340–450 на пункт в сутки — это физика движения, а не артефакт алгоритма). Удержанный маршрут может быть на переход длиннее кратчайшего |
| **0004** | Орбита на сцене приподнята ×1.42 | Картинка читаема, расчёты в настоящих километрах. Углы возвышения «на глаз» по сцене оценивать нельзя — только по цифрам |
| **0005** | Three.js и текстуры лежат в репозитории | Сервис работает без интернета; `file://` не работает из-за ES-модулей. Цена: +8 МБ, обновление three — ручная замена файла |
| **0006** | Сценарии кейса встроены в `data/scenarios.js` | Нет запросов и CORS-проблем на любом хостинге. Цена: менял `Данные/` — обязан пересобрать |
| **0007** | Расширения схемы — маска горизонта, наклонение плоскости, произвольные очереди | Файл жюри читается и выгружается без изменений; наши поля появляются только когда заданы. Два инварианта («маска 0 = правило кейса», «Walker 48/3/1 = кейс») закреплены тестами |
| **0008** | Вид абонента — страница-PWA на том же домене, а не нативное iOS | Житель ставит на экран «Домой», работает офлайн; числа совпадают по построению (один `sim.js`, одна сетка, один формат ссылки). Отклонено: Swift+TestFlight (нужен бэкенд и ревью), отдельный деплой, тумблер внутри страницы |
| **0009** | Синхронизация двух видов через `BroadcastChannel`, инженерный ведёт | Причина и следствие в одном кадре на защите. Граница: только окна одного браузера на одной машине. Канала оказалось мало из-за троттлинга скрытых вкладок — добавлено дублирование состояния в `localStorage` |

## 19. Границы модели и что сознательно не делали

### Границы модели (честно, и то же написано в окне «Как это работает» и в отчёте)

- Орбиты круговые, Земля сферическая — как в `geometry.py`. Реальные эфемериды, TLE и возмущения орбит не моделируются.
- Тень Земли цилиндрическая, Солнце неподвижно в течение суток — как `sunlight()` в эталоне.
- Задержка — только по длине пути со скоростью света. Без бортовой обработки, наземной сети,
  пропускной способности и очередей передачи (кейс это прямо разрешает: «расчёт пропускной способности…
  команда может добавить отдельным функционалом»).
- Рельеф и застройка учитываются как **геометрическая маска горизонта**; дифракция и отражения у зданий — нет.
- На сцене орбита приподнята ×1.42 для читаемости; все расчёты — в настоящих километрах.
- Монте-Карло использует `Math.random()` без сева: два прогона с одними параметрами дают разные цифры.
  Для полной воспроизводимости у жюри нужен был бы параметр seed.
- Оптимизатор состава очередей — жадный плюс структурные кандидаты, глобальный оптимум не гарантирован.
  Для первой очереди физический потолок ≈30% для худшего пункта: 16 аппаратов в одной плоскости
  не покрывают три пункта непрерывно, а при разнесении по плоскостям пропадает ISL (соседи только через 22.5°).

### Что не входит в этап (scope guard)

- **Бэкенд и база данных** — всё считается в браузере (ADR-0001).
- **Нативные мобильные приложения** — вместо них вид абонента сделан второй страницей того же сайта,
  которая ставится на экран «Домой» (ADR-0008: за платформу баллов не дают, цена высокая).
- **Энергетика, радиолинии, пропускная способность** — модель геометрическая, как в `geometry.py`.

### Если останется время

- glTF-модель реального аппарата (`vendor/satellite.glb` подхватится автоматически — сейчас процедурная модель);
- ускорение N-2 за счёт разделения геометрии сетки и маски отказов (оценка — около ×6);
- seed для Монте-Карло ради полной воспроизводимости.

## 20. Глоссарий

В проекте один термин на концепт, синонимы не используются — чтобы код, интерфейс и отчёт
говорили на одном языке. Имена в коде совпадают с этими терминами и с полями схемы `cosmo-A-1.0`:

| Термин | Что это |
|---|---|
| **Сценарий** | JSON схемы `cosmo-A-1.0` с параметрами среды, составом группировки, пунктами и периодами недоступности |
| **Конфигурация** | текущее (возможно изменённое) состояние сценария в интерфейсе — то, что сохраняют как вариант |
| **Плоскость** | орбитальная плоскость с `id`, `raan_deg`, `phase_deg`; в кейсе три по 16 аппаратов |
| **RAAN** | долгота восходящего узла плоскости; поворачивает плоскость вокруг оси Земли |
| **Фазирование** | общий сдвиг всех аппаратов плоскости вдоль орбиты |
| **Слот** | положение аппарата внутри плоскости; соседние через 22.5° — единственная дистанция, на которой в кейсе работает ISL внутри плоскости (≈2700 км < 3000 км) |
| **Очередь запуска / этап развёртывания** | `launch_batch` аппарата и `launch_stage` — сколько очередей уже считаются запущенными |
| **Активный аппарат** | запущен и не находится в периоде недоступности; только такие участвуют в ISL и видимости |
| **Видимость** | возвышение ≥ `min_elevation_deg` и не ниже маски горизонта в своём азимуте |
| **Маска горизонта** | угол закрытия неба рельефом или застройкой по 36 секторам азимута |
| **ISL** | ребро между двумя активными аппаратами: расстояние < `isl_range_km` и отрезок не пересекает Землю |
| **Снимок сети** | состояние на один шаг: положения, активность, рёбра ISL, видимость, тень |
| **Маршрут** | последовательность активных аппаратов от пункта до шлюза по существующим на этом шаге связям |
| **Липкий маршрут** | прежний маршрут сохраняется, пока живы все его звенья; новый ищется только при разрыве |
| **Переход** | ребро маршрута; число переходов = аппаратов + 1, включая две наземные линии |
| **Доступность** | доля отсчётов, на которых у пункта есть маршрут; основной показатель, цель 0.9 |
| **Перерыв / окно связи** | непрерывная серия отсчётов без маршрута / с маршрутом |
| **Запас прочности** | сколько одновременных отказов группировка выдерживает, не опускаясь ниже цели (0–2 по матрице N-1/N-2) |
| **Вариант** | сохранённая конфигурация со сводкой показателей и описанием отличий от файла — единица сравнения |
| **Вид абонента** | вторая страница сервиса, показывающая тот же расчёт глазами жителя пункта |
